# Soundcore Work D3200: непрерывный BLE realtime

Дата: 2026-11-22  
Рабочая ветка: `feature/soundcore-d3200-ble-input`  
Диагностическая версия: `1.0.61-d3200-continuous` (versionCode 65)

## Цель

Сохранять один GATT-сеанс и непрерывно передавать Opus-пакеты из последовательных файлов D3200 в существующий конвейер Pocket HUD:

`BLE notifications → D3200Session → AES-CTR → MediaCodec Opus → PCM16 mono 16 kHz → PocketService → Gemini Live`

Декодер MediaCodec не пересоздаётся при ротации файла: меняются только ключ файла, nonce и счётчик последовательности.

## Подтверждённые форматы протокола

### ECDH и ключи аудио

- `2E/01` — временный ECDH P-256 handshake.
- Ответ содержит публичный ключ устройства и проверяемый общий секрет.
- HKDF-SHA256 с контекстом `01 02 03` даёт session key.
- `1A/07` — запрос аудиофайла; realtime flag равен `1`.
- Заголовок `1A/07` — 87 байт: fileId (4), size (4), nonce (16), encrypted file key (46), session nonce (16), error code (1).
- Каждый транспортный audio slice — 166 байт: sequence (4), flags (1), encrypted Opus (160), reserved byte (1).
- Для каждого нового fileId требуется заново открыть заголовок и получить file key/nonce. Sequence начинается заново.

### Ротация и завершение

`1A/06` сообщает ID нового файла во время записи:

- legacy: `fileId:u32le + appendPreAudio:u8` (5 байт);
- текущий: `fileId:u32le + durationMs:u32le + appendPreAudio:u8` (9 байт).

`1A/0A` сообщает завершение передачи:

- текущий формат: `result:u8 + durationMs:u32le + fileId:u32le` (9 байт);
- короткий legacy-ответ может содержать только result.

`18/82` со статусом STOPPED используется как событие фактической остановки записи.

## Реализованное поведение

1. Новое событие `1A/06` переключает realtime на новый fileId независимо от того, кто начал запись — Pocket HUD или пользователь кнопкой диктофона.
2. Если новый fileId пришёл, пока ожидается заголовок предыдущего файла, ID ставится в ограниченную очередь (до 8 записей) и открывается после ответа заголовка.
3. При открытии каждого файла очищаются старый file key/nonce и сбрасывается sequence.
4. `1A/0A` для текущего файла завершает только текущий сегмент. GATT не закрывается; сессия ожидает следующий `1A/06`.
5. Позднее завершение старого файла с несовпадающим fileId игнорируется.
6. Событие STOPPED и потеря BLE-соединения по-прежнему завершают сессию.
7. Существующий MediaCodec и PCM-конвейер остаются общими для всех сегментов.

## Различия по версиям прошивки

Внешние реализации дают неодинаковые результаты, и их нельзя автоматически переносить на 03.56:

- `tacshi/Soundcore` документирует Windows BLE-проверки на D3200 с firmware `04.73`: realtime audio был проверен после unbind от Feishu; клиент не отправлял `0B/87` и не использовал Feishu account token.
- В исходниках `ws/soundcore` существует `DownloadClientMixin.stream_realtime()`: он отправляет realtime `1A/07`, принимает срезы и следует за ротацией `1A/06`; метод включён в BLE-клиент `SoundcoreClient`. При этом README того же проекта сообщает, что на его тестовом устройстве realtime-аудио не приходило по BLE и требовался iPhone-only MFi channel. Это расхождение между реализацией протокола и результатом испытания на конкретном устройстве; README не привязывает этот результат к версии firmware.
- Пользовательское устройство работает на firmware `03.56`. Ни один из этих источников не подтверждает BLE realtime именно на 03.56.

Поэтому текущая сборка исправляет state machine для BLE realtime, но окончательная возможность получения Opus по BLE на 03.56 остаётся аппаратной гипотезой. Критерий проверки — ответ `1A/07` с корректным 87-байтным заголовком и последующие `1A/08` или `1A/12` уведомления.

## Аппаратный результат firmware 03.56 (Pocket HUD 1.0.61)

Лог от 2026-11-22 подтверждает:

- BLE scan, GATT, MTU 512, notifications и `2E/01` ECDH проходят.
- Устройство сообщает новую запись через `1A/06` (payload length 8).
- Pocket HUD отправляет `1A/07` с payload length 9: offset 0, fileId LE, realtimeFlag 1.
- Ответ `1A/07`: status byte `01`, payload length 1; протокольный parser классифицирует одиночный payload `FF` как явный отказ.
- Ни одного `1A/08` или `1A/12` audio slice не получено; Opus/PCM/Gemini counters остаются нулевыми.

Это отказ на уровне устройства до ключа файла и декодирования. Причина не установлена: возможны ограничения firmware для live transfer, состояние привязки/лицензии или различия между прошивками.

### Read-only диагностика привязки

В Pocket HUD добавлено чтение advertisement bind bit по manufacturer data с маркером `soundc`. В лог пишется только `bound_bit_set`, `bound_bit_clear` или `unknown`; MAC и остальные manufacturer bytes не логируются. Этот флаг — подсказка о состоянии привязки, не доказательство необходимости `0B/8B`.

Также логируются payload запроса `1A/07` и короткий ответ устройства в hex, чтобы следующий тест зафиксировал фактические байты. Ни одна команда bind/unbind/auth/reset не отправляется.

## Диагностический fallback после отказа realtime

После аппаратного результата 1.0.61 в ветке добавлен read-only сценарий:

1. Если `1A/07` с `realtimeFlag=1` возвращает одиночный `FF` при успешном status byte, Pocket HUD больше не закрывает GATT немедленно.
2. Приложение ждёт, пока пользователь штатно остановит запись кнопкой D3200. Автоматическая остановка не отправляется.
3. После события STOPPED приложение запрашивает тот же fileId через `1A/07`, но с `realtimeFlag=0` и offset 0.
4. Если устройство отдаёт обычный конечный заголовок, Pocket HUD расшифровывает Opus-пакеты и проверяет `1A/0A`.
5. Если и обычный запрос отклонён, диагностическая сессия завершится с точным кодом отказа.

Это безопасная проверка чтения уже завершённого файла. Она не удаляет данные и не отправляет bind/auth/reset/OTA. Для аппаратного теста достаточно короткой записи 5–10 секунд, чтобы не передавать большой файл.

Результат разделит две гипотезы:
- если completed-file pull работает, но realtimeFlag=1 возвращает FF — BLE-доступ к файлам существует, а live transfer на 03.56 ограничен или требует отдельного режима;
- если оба режима возвращают FF — нужно исследовать состояние привязки/лицензии и политику прошивки, не выполняя unbind.

## Результат нового аппаратного теста (22.11.2026, 10:31–10:32)

На Motorola Edge 50 Pro с D3200 firmware 03.56:

- событие `1A/06` передало `fileId=1795339918`;
- realtime `1A/07` (`000000008EB6026B01`) вернул `FF`;
- после ручной остановки `18/82` устройство подтвердило STOPPED и повторно назван тот же ID файла;
- немедленный completed `1A/07` (`000000008EB6026B00`) тоже вернул `FF`;
- bind state `unknown` из рекламы, поэтому не делать вывод о привязке;
- Opus/PCM/Gemini по-прежнему 0.

**Ограничение прошлого диагностического эксперимента:** запрос готового файла отправлялся в ту же секунду, что пришёл STOPPED. Такого лога недостаточно, чтобы исключить задержку записи файла во флеш-память.

## Обновлённая безопасная диагностика

Новая версия после ручной остановки записи:

1. ждёт 3 секунды, не отправляя никаких команд;
2. запрашивает две страницы/формы read-only списка файлов: `1B/0E` и `1A/0E` (без записи, удаления или сброса);
3. отправляет completed `1A/07` с флагом `00`;
4. если снова получен короткий `FF`, ждёт дополнительные 5 секунд и повторяет **только один раз**;
5. затем либо принимает и декодирует аудио, либо фиксирует два отдельных отказа и завершает соединение.

Диагностика также пишет номер установленной сборки из Android PackageManager, не логирует содержимое заголовков, содержащих зашифрованный ключ файла, и при неизвестной привязке показывает только длины рекламных manufacturer-полей (без MAC).

После этих проверок можно более уверенно разделить «файл ещё не сохранён» и «устройство отказывает даже спустя несколько секунд». 0B/87, 0B/8B, 0B/8C, OTA, unbind/rebind, factory reset и удаление записей не выполняются.

## Аппаратный тест Pocket HUD 1.0.64, firmware 03.56 (2026-11-22 13:20)

Источник: пользовательский лог `pockethud-soundcore(2).log`, новая сессия 13:20:29–13:20:56:

- GATT, notifications и ECDH работают.
- `1A/06`: fileId `1795350043`, затем realtime `1A/07` (`000000001BDE026B01`) → `FF`.
- Пользователь остановил запись, `18/82` сообщил STOPPED в 13:20:52.
- После трёхсекундной паузы `1B/0E` и `1A/0E` оба вернули `FF`.
- Завершённый `1A/07` (`000000001BDE026B00`) вернул `FF`.
- Приложение перешло в `WAIT_OFFLINE_RETRY` в 13:20:55, но в 13:20:56 GATT закрылся **до запланированного повторного запроса**. Никаких команд после перехода в `WAIT_OFFLINE_RETRY` не было.
- По прежнему логированию источник закрытия не установить. Это может быть внешний вызов stop() или другой переход по жизненному циклу приложения; не утверждать, что 5-секундный retry состоялся.
- BLE advertisement: `manufacturerSpecificData` содержит 6 байт. В прежнем коде искался необязательный ASCII-маркер `soundc` в длинном payload, поэтому состояние привязки ошибочно оставалось `unknown`.

### Исправления для следующего теста

- Android `ScanRecord.getManufacturerSpecificData()` исключает 2-байтовый company ID. Согласно `tacshi/Soundcore` bind flag находится на байте 6 объединённого manufacturer буфера, то есть на байте 4 шестибайтового Android payload. Маркер `soundc` для чтения флага не обязателен, поскольку BLE UUID D3200 уже подтверждён.
- Парсер отдельный и протестирован для шестибайтовых и более длинных manufacturer payload; полный payload/MAC не логируются.
- Добавлено явное событие `external_ble_stop_requested` в точке запроса остановки, `session_stop_requested` с фазой и `ble_finish shuttingDown`. Это позволит отличить ручное завершение Pocket HUD от таймаута и разрыва радиоканала.
- Автоматический вызов опасных команд (bind/unbind/reset/OTA) по-прежнему запрещён.

### Исследование сторонних реализаций

- `tacshi/Soundcore` успешно передавал realtime и завершённые файлы на firmware 04.73 после отвязки Feishu. Этот факт сам по себе не доказывает, что отвязка необходима на 03.56 — менять состояние D3200 запрещено.
- `andrewseago/d3200-ble-note-downloader` сообщает об успешном BLE-скачивании записей с помощью альтернативного набора подготовительных команд, включая статический auth token и time sync. Его формат команд/ответов и порядок handshake нельзя механически переносить на текущий `1A/07`; перед экспериментами потребуется сверка совместимости с firmware 03.56. Текущее приложение не отправляет auth token или time sync.

### Следующее изменение

Серверный компонент `PocketService` теперь записывает причину `stopD3200(reason)`: `microphone_source_change`, `translation_engine_change`, `service_destroy`, состояние движка/сокета. Дополнительно логируются события закрытия/ошибки Gemini без текста запросов, API ключей или аудио. UI подсказывает **не останавливать Pocket HUD**, когда пользователь останавливает запись на устройстве и приложение ожидает повторного запроса.

### Дополнительный независимый протокол

Проект `imraywang/openbean` (Apache-2.0) имеет аппаратно проверенный BLE realtime и offline на **firmware 04.82**. Его протокол использует тот же формат `1A/07` (offset, file ID, realtime flag) и ECDH `2E/01`; bind/unbind не выполняются. Это подтверждает валидность формата Pocket HUD, но не доказывает доступность передачи без авторизации именно на связке **03.56 + bound device**. Исходник: https://github.com/imraywang/openbean/blob/master/docs/PROTOCOL.md.

Если второй отложенный запрос в будущей сессии снова ответит `FF`, следующие безопасные исследования: **локальный анализ HCI трассы официального Soundcore App** с удалением идентификаторов, содержимого аудио и ключей перед обменом результатами. Запрещены OTA, unbind/rebind и любые изменения состояния привязки.

## Авторизация 0B/8B: ограничения безопасности

В этой версии не отправляются `0B/87`, `0B/8B` или `0B/8C`.

В `ws/soundcore` описан отдельный механизм secure binding/authentication: UID (19 UTF-8 байт), timestamp, binding key (32 байта) и свежий nonce (16 байт). README проекта указывает, что эти pairing/authentication flows соответствуют SDK, но не были проверены на самом диктофоне. Хранение binding key предлагается реализовывать через системное защищённое хранилище.

В `tacshi/Soundcore` ECDH handshake `2E/01` используется для расшифровки realtime-аудио; bind/unbind вынесены в отдельные явные действия пользователя. Поэтому binding/authentication не считаются доказанным обязательным условием BLE realtime. Не выполнять bind, unbind, silent reset или OTA для проверки этой гипотезы.

## Отдельный альтернативный транспорт: Dictation Mode

Официальная документация soundcore / Typeless (проверено 2026-11-22):

- Dictation Mode превращает D3200 во внешний Bluetooth-микрофон (audio input only); аудиовыход не поддерживается.
- Для уже проданных устройств официальная статья требует firmware 03.58 или новее.
- Вход в режим: три быстрых нажатия боковой кнопки; синяя индикация; затем сопряжение в системных Bluetooth settings.
- В режиме Dictation устройство подключается только к одному телефону/компьютеру одновременно; выход из режима — отпускание боковой кнопки.
- Официальное объявление Anker Japan сообщает, что firmware v03.66 rollout был приостановлен 17 ноября 2026 из-за дефекта; более свежего подтверждения возобновления в доступных источниках на 22 ноября не найдено.

Источники:
- https://service.soundcore.com/article-description/How-to-Use-soundcore-Work-with-Typeless
- https://service.soundcore.com/article-description/How-to-Connect-soundcore-Work-to-Typeless
- https://prtimes.jp/main/html/rd/p/000000691.000016775.html

На пользовательском D3200 установлена 03.56, поэтому Dictation Mode пока не является доступным тестовым путём. Не запускать OTA. Если Anker возобновит исправленную прошивку, можно будет отдельно реализовать и проверить стандартный Android Bluetooth microphone input path в Pocket HUD — это будет альтернативой BLE 1A/07, а не частью текущего протокола.
## Автоматические тесты

Добавлены проверки:

- legacy/current layouts события `1A/06`;
- current/short layouts `1A/0A`;
- переход с fileId 42 на 43 при записи, начатой пользователем;
- игнорирование завершения предыдущего файла после перехода;
- сброс sequence: пакет 5 в старом файле и пакет 0 в новом;
- очередь ротации, пришедшей до ответа `1A/07`;
- ожидание следующего файла после `1A/0A` без закрытия GATT.

## Ограничения приёмки

Эти изменения проверяют state machine и payload parsing на JVM. Они не доказывают, что прошивка 03.56 реально отправляет BLE Opus на конкретном устройстве. Нужен тест на Motorola Edge 50 Pro:

1. Запустить Pocket HUD и выбрать Soundcore Work.
2. Если приложение попросит, начать запись физической кнопкой D3200.
3. Произнести речь и проверить рост счётчиков Opus/PCM/Gemini.
4. Продолжить запись через ротацию файла и проверить, что новые `1A/07` запросы не закрывают GATT, а счётчики продолжают расти.
5. Проверить перевод в наушниках.
6. Остановить запись штатно и сохранить диагностический лог.

Не выполнять OTA, factory reset, bind/unbind или другие изменяющие состояние команды.
