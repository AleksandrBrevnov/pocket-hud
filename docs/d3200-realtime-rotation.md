# Soundcore Work D3200: непрерывный BLE realtime

Дата: 2026-11-22  
Рабочая ветка: `feature/soundcore-d3200-ble-input`  
Диагностическая версия: `1.0.61-d3200-continuous` (versionCode 65)

## Цель

Сохранять один GATT-сеанс и непрерывно передавать Opus-пакеты из последовательных файлов D3200 в существующий конвейер Pocket HUD:

`BLE notifications → D3200Session → AES-CTR → MediaCodec Opus → PCM16 mono 16 kHz → PocketService → Gemini Live`

Декодер MediaCodec не пересоздаётся при ротации файла: меняются только ключ файла, nonce и счётчик последовательности.

## Подтверждённые форматы протокола

### ECDH и ключи аудио

- `2E/01` — временный ECDH P-256 handshake.
- Ответ содержит публичный ключ устройства и проверяемый общий секрет.
- HKDF-SHA256 с контекстом `01 02 03` даёт session key.
- `1A/07` — запрос аудиофайла; realtime flag равен `1`.
- Заголовок `1A/07` — 87 байт: fileId (4), size (4), nonce (16), encrypted file key (46), session nonce (16), error code (1).
- Каждый транспортный audio slice — 166 байт: sequence (4), flags (1), encrypted Opus (160), reserved byte (1).
- Для каждого нового fileId требуется заново открыть заголовок и получить file key/nonce. Sequence начинается заново.

### Ротация и завершение

`1A/06` сообщает ID нового файла во время записи:

- legacy: `fileId:u32le + appendPreAudio:u8` (5 байт);
- текущий: `fileId:u32le + durationMs:u32le + appendPreAudio:u8` (9 байт).

`1A/0A` сообщает завершение передачи:

- текущий формат: `result:u8 + durationMs:u32le + fileId:u32le` (9 байт);
- короткий legacy-ответ может содержать только result.

`18/82` со статусом STOPPED используется как событие фактической остановки записи.

## Реализованное поведение

1. Новое событие `1A/06` переключает realtime на новый fileId независимо от того, кто начал запись — Pocket HUD или пользователь кнопкой диктофона.
2. Если новый fileId пришёл, пока ожидается заголовок предыдущего файла, ID ставится в ограниченную очередь (до 8 записей) и открывается после ответа заголовка.
3. При открытии каждого файла очищаются старый file key/nonce и сбрасывается sequence.
4. `1A/0A` для текущего файла завершает только текущий сегмент. GATT не закрывается; сессия ожидает следующий `1A/06`.
5. Позднее завершение старого файла с несовпадающим fileId игнорируется.
6. Событие STOPPED и потеря BLE-соединения по-прежнему завершают сессию.
7. Существующий MediaCodec и PCM-конвейер остаются общими для всех сегментов.

## Различия по версиям прошивки

Внешние реализации дают неодинаковые результаты, и их нельзя автоматически переносить на 03.56:

- `tacshi/Soundcore` документирует Windows BLE-проверки на D3200 с firmware `04.73`: realtime audio был проверен после unbind от Feishu; клиент не отправлял `0B/87` и не использовал Feishu account token.
- В исходниках `ws/soundcore` существует `DownloadClientMixin.stream_realtime()`: он отправляет realtime `1A/07`, принимает срезы и следует за ротацией `1A/06`; метод включён в BLE-клиент `SoundcoreClient`. При этом README того же проекта сообщает, что на его тестовом устройстве realtime-аудио не приходило по BLE и требовался iPhone-only MFi channel. Это расхождение между реализацией протокола и результатом испытания на конкретном устройстве; README не привязывает этот результат к версии firmware.
- Пользовательское устройство работает на firmware `03.56`. Ни один из этих источников не подтверждает BLE realtime именно на 03.56.

Поэтому текущая сборка исправляет state machine для BLE realtime, но окончательная возможность получения Opus по BLE на 03.56 остаётся аппаратной гипотезой. Критерий проверки — ответ `1A/07` с корректным 87-байтным заголовком и последующие `1A/08` или `1A/12` уведомления.

## Аппаратный результат firmware 03.56 (Pocket HUD 1.0.61)

Лог от 2026-11-22 подтверждает:

- BLE scan, GATT, MTU 512, notifications и `2E/01` ECDH проходят.
- Устройство сообщает новую запись через `1A/06` (payload length 8).
- Pocket HUD отправляет `1A/07` с payload length 9: offset 0, fileId LE, realtimeFlag 1.
- Ответ `1A/07`: status byte `01`, payload length 1; протокольный parser классифицирует одиночный payload `FF` как явный отказ.
- Ни одного `1A/08` или `1A/12` audio slice не получено; Opus/PCM/Gemini counters остаются нулевыми.

Это отказ на уровне устройства до ключа файла и декодирования. Причина не установлена: возможны ограничения firmware для live transfer, состояние привязки/лицензии или различия между прошивками.

### Read-only диагностика привязки

В Pocket HUD добавлено чтение advertisement bind bit по manufacturer data с маркером `soundc`. В лог пишется только `bound_bit_set`, `bound_bit_clear` или `unknown`; MAC и остальные manufacturer bytes не логируются. Этот флаг — подсказка о состоянии привязки, не доказательство необходимости `0B/8B`.

Также логируются payload запроса `1A/07` и короткий ответ устройства в hex, чтобы следующий тест зафиксировал фактические байты. Ни одна команда bind/unbind/auth/reset не отправляется.

## Авторизация 0B/8B: ограничения безопасности

В этой версии не отправляются `0B/87`, `0B/8B` или `0B/8C`.

В `ws/soundcore` описан отдельный механизм secure binding/authentication: UID (19 UTF-8 байт), timestamp, binding key (32 байта) и свежий nonce (16 байт). README проекта указывает, что эти pairing/authentication flows соответствуют SDK, но не были проверены на самом диктофоне. Хранение binding key предлагается реализовывать через системное защищённое хранилище.

В `tacshi/Soundcore` ECDH handshake `2E/01` используется для расшифровки realtime-аудио; bind/unbind вынесены в отдельные явные действия пользователя. Поэтому binding/authentication не считаются доказанным обязательным условием BLE realtime. Не выполнять bind, unbind, silent reset или OTA для проверки этой гипотезы.

## Автоматические тесты

Добавлены проверки:

- legacy/current layouts события `1A/06`;
- current/short layouts `1A/0A`;
- переход с fileId 42 на 43 при записи, начатой пользователем;
- игнорирование завершения предыдущего файла после перехода;
- сброс sequence: пакет 5 в старом файле и пакет 0 в новом;
- очередь ротации, пришедшей до ответа `1A/07`;
- ожидание следующего файла после `1A/0A` без закрытия GATT.

## Ограничения приёмки

Эти изменения проверяют state machine и payload parsing на JVM. Они не доказывают, что прошивка 03.56 реально отправляет BLE Opus на конкретном устройстве. Нужен тест на Motorola Edge 50 Pro:

1. Запустить Pocket HUD и выбрать Soundcore Work.
2. Если приложение попросит, начать запись физической кнопкой D3200.
3. Произнести речь и проверить рост счётчиков Opus/PCM/Gemini.
4. Продолжить запись через ротацию файла и проверить, что новые `1A/07` запросы не закрывают GATT, а счётчики продолжают расти.
5. Проверить перевод в наушниках.
6. Остановить запись штатно и сохранить диагностический лог.

Не выполнять OTA, factory reset, bind/unbind или другие изменяющие состояние команды.
