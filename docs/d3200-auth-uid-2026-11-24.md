# D3200 firmware 03.56 — 40-character account identifier confirmation

Date: 2026-11-24. Source: local read-only Termux output supplied by the device owner.
No raw UID, keys, account identifiers, Bluetooth addresses, nonces or ciphertext are included.

## Local findings

A read-only script scanned the installed Soundcore Android app's private shared preferences and reported:

- `key_account_uid`: one non-empty entry
- UID length: 40 characters
- UID format: exactly 40 hexadecimal characters
- Matching `*_authKey_data` namespace: one
- Direct case-insensitive match between UID and the 40-hex key namespace: **true**
- SHA-1(UID) vs key namespace match: **false**
- No observed 19-character UID

This establishes that the preference namespace uses the 40-character account identifier directly. It does **not** establish a plaintext format or prove that this UID participates in command `0B/8B`.

## Cross-check with on-device BTSnoop

Official Soundcore 5.0.39 on this same firmware 03.56 sent one `0B/8B` payload of exactly 62 bytes:

`[2C] [44 ciphertext bytes] [10] [16 nonce bytes]`

The device responded with a one-byte `00` result and successful frame status. Official `1A/A7` and file-list commands succeeded after that.

The published protocol report in
https://github.com/tacshi/Soundcore/issues/9
describes `AES-256-CTR(binding_key, fresh_nonce, uid_ascii_40 || timestamp_le32)` for D3200 firmware 03.66. This produces a 44-byte ciphertext and the observed 62-byte envelope. Our new 40-byte UID finding makes that candidate structurally plausible for 03.56, **not yet verified** for the user's device.

## Branch implementation boundary

`D3200Authentication.envelope()` implements the candidate **only as an offline builder**, with:
- strict 40-hex-character account ID validation;
- 32-byte binding-key and 16-byte nonce validation;
- 32-bit little-endian Unix seconds encoding;
- AES-256-CTR using the existing `D3200Crypto.ctr` helper;
- length-prefixed `44 + 16` encrypted/nonce envelope;
- no real account data or key material in source and test vectors.

`D3200Session` is unchanged: the helper is **not invoked during BLE connection** and sends no command. This avoids wrongly assuming a credential, decrypting unrelated encrypted preference values, or replaying a captured request. Existing recording transfer remains blocked on the bound device until authorization and key unwrap are established.

## Remaining blockers

1. Reliably obtain the *preexisting* 32-byte binding credential without rebinding, resetting, changing firmware or exporting secrets to GitHub.
2. Prove the plaintext/timestamp/cipher candidate is correct for firmware 03.56 using authorized test data or well-grounded implementation evidence.
3. Determine the correct 03.56 file-key unwrap procedure. The official 03.56 trace did **not** send `2E/01`; the project's current `D3200Crypto.unwrap` assumes a session key from that newer handshake path.
4. Establish whether *unpaused* live audio can be delivered on 03.56; the official trace proves a paused burst of 446 encrypted Opus units only.
5. Never send `1A/10` deletion, `0B/87` bind/unbind, OTA or reset commands.

Unit tests cover the envelope shape and a deterministic AES-CTR round-trip with a **synthetic** UID/key/nonce. Tests and real-device authorization have not been executed as part of this code-only commit.
